# NTBA0002: Uncovered interactive entry method should use try/catch

| Default severity | Code fix |
| --- | --- |
| Info (Warning in strict mode) | No |

## Why it matters

An event handler that throws without `try/catch` surfaces as an unhandled exception in the component. In Blazor Server that can terminate the circuit unless an `ErrorBoundary` above the component catches it. This rule checks the entry methods bound to interactive regions that have no `ErrorBoundary` coverage.

## What is reported

- An interactive entry method, reached from an independently interactive render region with no `ErrorBoundary` coverage, that performs failure-prone work with no `try/catch` handling on the path.
- Only entry methods are reported. Helper methods do not warn on their own, and the warning stays on the entry method even when the risky call is in a helper.
- A helper needs no `try/catch` when every reachable caller already has one.
- A method that only delegates to a safe member method is not reported.
- Trivial local state mutation alone is not reported.
- Lifecycle, dispose, and JS interop concerns are covered by NTBA0003 through NTBA0006.
- Handling: a `catch` that does not throw contains the failure, unless it only catches cancellation (`OperationCanceledException`, `TaskCanceledException`, a `when` filter on `IsCancellationRequested`) or `JSDisconnectedException`. A `catch { throw; }`, or one that logs and rethrows, propagates the failure and does not count. Whether the catch logs is reported separately by NTBA0008, so a swallowed exception is reported once.
- Not failure-prone: calls returning a Result type (a `bool` property such as `IsSuccess`, `IsSuccessful`, `HasFailed` or `IsError`, directly or through `Task<T>`), `EventCallback` invocations, toast and snackbar services, and built-in browser functions such as `confirm` called through JS interop.

## How to fix

Before:

```razor
@rendermode InteractiveServer

<button @onclick="Save">Save</button>

@code {
    private void Save()
    {
        Repository.Save();
    }
}
```

After:

```razor
@rendermode InteractiveServer
@using Microsoft.Extensions.Logging

<button @onclick="Save">Save</button>

@code {
    [Inject] private ILogger<EditorPage> Logger { get; set; } = default!;

    private void Save()
    {
        try
        {
            Repository.Save();
        }
        catch (Exception exception)
        {
            Logger.LogError(exception, "Save failed.");
        }
    }
}
```

Wrapping the whole region in an `ErrorBoundary` (see NTBA0001) is the other option.

## Configuration

- Failure-prone detection: `ntba.failure_prone_type_suffixes`, `ntba.failure_prone_method_prefixes`, `ntba.safe_types`, and `ntba.failure_handling_methods` decide which calls count as failure-prone.
- `ntba.assume_owner_error_boundary = true`: suppresses this rule for component libraries whose consumers own the `ErrorBoundary`.
- Strict mode: `<NTBlazorAnalyzerMode>strict</NTBlazorAnalyzerMode>` raises the severity to Warning.

See [Configuration](README.md#configuration) for the setting syntax.

## Suppressing

In `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.NTBA0002.severity = none
```

In code:

```csharp
#pragma warning disable NTBA0002
// entry method
#pragma warning restore NTBA0002
```
